2. Key aspects of our proposed approach

While we broadly agree with the direction outlined in the brief, there are a few architectural principles we believe will make the platform more robust

a. Maintain our own canonical music entity layer

Spotify can be an important metadata source and ISRC can be a key identifier, but we would recommend maintaining an independent canonical music entity model

b. Dedicated entity resolution with confidence scoring

Cross-platform matching will be one of the most critical parts of the solution. We would combine identifiers such as ISRC, where available, with title, artist, duration, album/release,

AI/GenAI can assist with metadata interpretation and ambiguous matching, but the underlying matching logic should remain deterministic 
and auditable.

c. Connector-based source architecture

Spotify, YouTube, JioSaavn, others and future social platforms should be treated as independent data sources through a connector-based framework rather 
than tightly coupling the core platform to any one source. This allows individual collection mechanisms to evolve without affecting the rest of the system.

d. Raw data and provenance

Where permitted, we would retain the original source response/raw capture before transformation. This provides auditability and allows the data to be reprocessed 
if parsing or transformation logic changes. Each metric should retain its source, capture timestamp, processing status and relevant quality or estimation flags.

The daily snapshot should be treated as the primary fact, with daily gains, 7-day/28-day growth, rankings and other derived metrics calculated

Once sufficient reliable data is available, the platform can be extended with AI/ML capabilities for metadata enrichment, anomaly detection, trend identification and
