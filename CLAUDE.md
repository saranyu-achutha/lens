# Market Lens: project context

Saranyu Technologies is building a release market-data platform for Times Music (client contact: Amit Bardhan; Saranyu lead: Suresh BG). The requirements are in the email thread at `lens/req..html` (the filename has two dots).

- **Phase 0 targets:** at least 95% of releases discovered within 24 hours, at least 90% matched across platforms, at least 99% of daily readings captured, and at most 10% of matches needing manual review.
- **Data rules:** daily snapshots kept indefinitely. The client asked for YouTube every 6 hours in a video's first 7 days; on 2026-11-02 the user set every source to one reading a day per item; **on 2026-11-06 YouTube videos in their first 7 days went to every 8 hours, then once a day** (`youtube.fresh_every_hours` = 8, `fresh_days` = 7; about 2,500 quota units a day); everything else once a day (`songs.jiosaavn_refresh_hours` = 24). Both are changeable on the Console's Collection schedule page (YouTube 6, 8, 12 or 24 h).
- **Daily cleanup (2026-11-03, `lens/cleanup.py`, worker job `cleanup` after 03:00 server time):** frees disk without losing anything ("keep data for debugging"). It takes today's backup if the 02:30 cron missed it (VACUUM INTO, gzipped, 14 days kept; the cron runs `python3 -m lens.cleanup backup`). Raw API replies older than 7 days move from `raw_capture` to `data/archive/raw_capture/*.jsonl.gz`. CSV files left in `out/` are gzipped into `out/archive/`. Loose `.db` copies in `data/backups` are gzipped. The database's free pages are returned to the disk (incremental auto-vacuum). Settings are under `config.json` → `cleanup`; results show on the Status page.
- **No CSV files on disk (2026-11-03):** runs no longer write CSVs. The Outputs page (`lens/exports.py`, `/api/datasets*`) shows each dataset (song daily totals per day, songs, song metadata, YouTube videos, Spotify label crawl) straight from the database, paged and filterable. Download builds the CSV in memory and sends it; nothing is kept. **CSV downloads carry no IDs or links (user rule, 2026-11-04):** every download (Outputs datasets, Reports, Daily data, per-platform items, songs export, archived CSVs) goes through `exports.IdFreeWriter`, which drops any column ending in `_id`, `_ids` or `url` (song_id, platform/video/Spotify track IDs, YouTube/Spotify links). Songs are named by title with all their other details; ISRC and UPC stay. The on-screen tables are unchanged. Older CSVs stay downloadable from `out/archive/`.
- **Output:** a model ready for Power BI.
- **No AI or ML:** all matching is rule-based.

The code lives in `lens/` and runs on the server as `/home/ubuntu/lens`. This laptop holds a copy. See `lens/README.md` for how to run it and how the pipeline works.

- **Database locks (fixed 2026-11-05):** a loop that calls the network must commit as it goes; one transaction held across many calls locks out every other writer (they wait 5 minutes, then fail). On 5 Nov the Deezer step held the lock ~24 minutes (01:47–02:11 UTC); the Spotify play-count run then failed to save its result, its thread died and the browser lane stayed "running" for 6 hours (no Spotify plays or Instagram). Rule: in any loop that calls the network, commit pending writes before the call.

Each batch's values are stored once (`import_file(only=…)`). Shorts: header → any header renderer → smallest data block with "N Shorts" + owner channel id (owner never guessed); `initial_data` uses raw_decode; "no sound page" marks only after the guards pass at the end of the run. A learned marker is kept after 3 items (`state heal_hint:<reader>`); one unreadable page a day is kept in `data/heal_samples/<reader>/<day>.html.gz` (7 days). Alerts `heal:<reader>` (warning: on a fallback, readings continue; critical: held), `suspect:<reader>` (20+ a day). Console: Missed readings → **Page readers** card (`/api/heal`); every page that fails to load shows "This page could not load … Retry" (`pageGuard` in app.js) and failed background refreshes a toast, instead of a blank page.
- **Pause and resume jobs (2026-11-04, `lens/pause.py`):** Developer dashboard → Job control. **Pause** lets running jobs finish and starts nothing new; **Pause now** also stops running jobs at their next safe point (between songs, pages or videos; data read so far is kept; the run is recorded as `paused`). Every job or only some (e.g. Instagram alone). Paused runs don't count as "ran recently", so on resume they continue straight away from what is still due. ## Songs, versions and merging (2026-10-23)

- One song = many YouTube uploads (video, lyric, audio, short, teaser); per-video stats plus totals by type. Shorts and teasers only join existing songs.
- One song can have several Spotify tracks (`match_method='same_recording'`), linked from the same search result.
- Window set to 2026-09-15 → 2026-10-15 (`config.window()`).
- `lens/merge.py`: configurable merge rules (`config.json` → `merge`). Merges are recorded in `review_decision` (action `merge`) and can be undone. `song_alias` keeps merged names, so regrouping preserves merges; `merge_rejection` remembers "not the same".

## Song metadata (2026-10-23)

- `lens/metadata.py` parses the credits blocks in YouTube descriptions and adds Spotify data, language, category and occasion rules into `song_meta` (one row per song, field and value, with `value_key` and `source`). It is rebuilt each run and after Review decisions and merges.
- The Explore page and `/api/meta/top` and `/api/meta/detail` give metrics per value. The YouTube `videos.list` call now also requests `snippet` (tags, audio language, category) at no extra quota.
- Known gaps: spelling variants of the same person aren't merged (Sublashini / Sublahshini); honorifics stay in names ("Natural Star Nani").

## Main modules (`lens/lens/`)

| Module | What it does |
|---|---|
| `match.py` | Rule-based scoring: title .55, artist .15, film .10, duration .10, date .10. A match is automatic at a total ≥ .75 with title ≥ .85, and goes to review at ≥ .55. Remix, male/female and "X version" variants never match. |
| `songs.py` | Groups videos into songs, does the Spotify lookup (songs not found are rechecked every 3 days), sets the status (new release if on Spotify at most 30 days before the first YouTube upload, otherwise older release, or not on Spotify), takes Deezer readings and writes the songs CSV. |
| `sync_youtube.py` | Collects uploads, takes readings and runs matching. |
| `youtube.py` | YouTube API client. It takes a single `YOUTUBE_API_KEY` and counts quota units. |
| `spotify.py` | Spotify client with a per-run call budget and quota detection. |
| `jobs.py` | Runs jobs and pipelines, runs the scheduler (pipeline every 6 hours) and the health watcher. |
| `review.py` | Decision log with exact undo. |
| `studio.py` | HTTP server and API. |
| `static/` | The UI. |
